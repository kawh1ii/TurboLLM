# TurboLLM 重写说明与实测结论

本轮完成了可运行、接入真实 vLLM 的调度与 KV 预算原型，以及完整回归材料。**实测没有证明自定义策略能够稳定超过原生或调优后的 vLLM。** 求职时应表述为“推理调度与资源管理原型”，不能写成已经实现通用加速。

## 实际改写的内容

- `src/turbollm/policy.py`：不可变请求视图、非负耗时模型、执行反馈修正、逐请求 token 配额、等待补偿和未来未分配 KV 块账本。
- `src/turbollm/vllm_scheduler.py`：读取真实请求和块表；在前缀命中已知后核算准入；接入取消、完成、抢占及模型返回；记录实际分配与成本。
- `patches/vllm-0.32.0-scheduler.patch`：将上述决策接入实际调度/分配路径，版本和源码散列校验后才能应用，可恢复上游原始文件。
- 修正了两处自身实现边界：RUNNING 顺序会影响原生抢占对象；已有输出的请求在抢占后仍可能处于多 token 重算阶段，不能只凭 prompt 边界判断 decode。

模型执行、attention kernel、物理 KV 分配、块表及引用计数均复用上游。没有把它们记作本项目自行实现的算子或引擎。

## 验证结果

- 纯策略及测量回归：**21 项通过**。
- 严格输出对照：17 个边界/自然语言/并发用例，加 16 个同时到达并触发真实抢占与重算的压力请求，**33/33 完整 token ID 一致**。条件为 Qwen2.5-3B、BF16、eager、上游 batch-invariant 模式。
- 完成 14 个验证阶段、87 份请求级运行记录，共 **3536 条记录**：3530 条完成、6 条按设计取消，没有错误或超时。另有明确排除在性能统计之外的预热。
- 审核 30 份引擎 trace、63,259 条调度记录，其中自定义策略记录 31,289 条；实际配额未超预算，排空后的请求、物理空闲块及自定义账本均通过检查。

普通 BF16 模式中，原生引擎改变分块也出现输出差异；严格数值模式下的通过不能外推为任意普通批处理都逐 token 一致。详见 [排错记录](docs/DEBUG_LOG.md) 和 `results/correctness-final/`。

## 环境与公平比较

单张 RTX 4090 24GB；Ubuntu 22.04；Python 3.12.3；PyTorch 2.13.0+cu130；vLLM 0.32.0；Qwen2.5-3B/7B-Instruct BF16。完整软件锁和模型文件 SHA-256 清单随附。

种子 61 用于成本校准、62 用于有限候选调优；63/64/65 用于冻结后的评估，66 用于追踪写盘检查。上游候选选中 256 token 阈值、5% 水位及自适应阈值；自定义策略选中 16-token 未来窗口。候选搜索不等于找到全局最优配置。

正式性能实验双方统一开启默认编译/CUDA Graph。下面的主要结果使用**完全恢复原始源码、直接运行原生 Scheduler 的基线**，不使用追踪包装；自定义策略也关闭 trace 写盘。各模式的实际源码状态保存在对应 `*.source-state.json`。

负载是长度/到达可控的合成 token 请求；普通形状为 128/384/1024 token 输入和 128/256 token 输出。自然容量和压力场景分别测量；256 KV 块是人为受控压力条件，不能代替线上显存分布。目标为 TTFT ≤1000ms 且 TPOT ≤40ms；达标请求/s 以包含排空时间的完整墙钟计。

## 主要端到端结果

表内速率、P95 均为三次独立运行的中位数；达标/到达为三次运行的合计。没有将三次运行描述为统计显著性证据。

|条件|策略|输出 token/s|达标请求/s|TTFT P95 ms|TPOT P95 ms|达标/到达|
|---|---|---:|---:|---:|---:|---:|
|3B 自然容量|原生|938.17|5.497|85.39|15.91|144/144|
|3B 自然容量|上游调优|928.26|5.439|130.97|16.18|144/144|
|3B 自然容量|自定义策略|907.44|5.317|101.15|17.61|144/144|
|3B 256 KV 块|原生|470.69|0.517|8822.30|14.79|27/144|
|3B 256 KV 块|上游调优|453.72|0.556|9174.45|21.19|30/144|
|3B 256 KV 块|自定义策略|417.29|0.442|11529.25|19.40|26/144|

自然容量下，自定义策略吞吐略低；受控压力下吞吐、首 token 尾延迟和达标请求速率均未优于两种原生基线。因此，本轮不支持“普遍更快”或“在 KV 紧张时必然更优”的结论。

## 扩展条件与消融

下表保留统一追踪包装以进行机制核查，不能与上面未经包装的数字直接合并比较：

|条件|策略|输出 token/s|达标请求/s|TTFT P95 ms|TPOT P95 ms|达标/到达|
|---|---|---:|---:|---:|---:|---:|
|3B 8K 提示词|原生|476.34|2.791|530.94|27.87|72/72|
|3B 8K 提示词|自定义策略|446.81|2.241|1187.94|30.57|61/72|
|7B 256 KV 块|原生|254.01|0.368|8145.12|24.77|23/96|
|7B 256 KV 块|自定义策略|242.85|0.364|9556.93|28.35|24/96|

7B 使用独立校准的耗时系数；它证明在该模型与配置下能够运行，不构成跨模型普适收益。8K 条件的自定义策略也出现退化。

|条件|策略|输出 token/s|达标请求/s|TTFT P95 ms|TPOT P95 ms|达标/到达|
|---|---|---:|---:|---:|---:|---:|
|完整策略|自定义策略|395.45|0.393|11956.45|21.09|25/144|
|同一压力条件|关闭耗时预算|422.07|0.468|10509.30|19.29|27/144|
|同一压力条件|关闭未来块预留|397.08|0.385|11964.13|17.49|23/144|

关闭耗时预算后，本组高压力负载的吞吐和达标请求速率有所恢复，提示时间预算策略需要继续改进，不能将该模块的存在当作收益证明。

在统一追踪的 3B 压力对照中，规划器 P95 为 2.97ms，自定义调度总 P95 为 5.27ms；原生策略加相同追踪包装为 1.37ms。三次运行合计，原生/自定义抢占次数为 44/42，但重算 token 为 5003/11778。减少抢占次数并不自动意味着更少的重计算。这些是机制观察，没有把完整吞吐差距全部归因于某一项。

成本模型校准的交替步留出 MAE 为 0.96ms，但这种留出不是跨负载泛化验证；8K 实测也说明不能仅凭校准误差就声称具有通用预测精度。

## 审查与复现

- [完整自动复算表](results/final/REPORT.md)、`summary.json`、请求输入/输出和服务端日志均随附。
- `tools/verify_results.py` 可在不重跑 GPU 的情况下核对纯策略测试、输出 ID、源码状态、全部调度配额与排空状态；结果为 `results/final/verification.json`。
- `tools/report.py --root results/final` 可重新生成汇总表和证据散列；`README.md` 给出重跑实验命令。
- 最初 macOS 传输携带的三份非执行元数据曾进入旧聚合指纹。它们的原始字节单独归档，`source-hash-audit.json` 和 `verify_sources.py` 可重建旧指纹并核对可移植的真实 Python 源码。没有为解决指纹差异而改写历史结果。
- 开发版源码与负面结果保存在 `results/development-v1/`、`development-v2/`，不混入最终版本性能结论。

## 简历表述边界

可以强调源码级调度扩展、按请求分配预算、KV 资源会计、抢占恢复状态、数值路径排查和可复现验证。当前不应写“显著加速 vLLM”“重写 PagedAttention”或“实现高性能 CUDA 算子”。

后续若继续以性能优化为目标，应优先处理已测得的 Python 规划热路径开销，并重新设计时间预算对实际接纳 batch 的处理；这属于后续迭代，不是本轮已完成成果。
