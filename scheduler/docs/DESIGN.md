# 设计、正确性与证据边界

## 一个可检验的问题

长提示词 prefill 与 decode 混合时，单纯限制每步 token 数不直接限制该步执行时间；只检查当前分配也不等同于为在途请求的增长预留空间。

问题是：一个可解释的逐请求计划，能否在部分混合负载中提高满足延迟目标的请求完成率，并减少高 KV 压力下的重计算？低负载和吞吐损失必须同时报告。

## 与上游的边界

锁定上游 vLLM 0.32.0 / `5df63a7203cdb9328d824a27b682e77c7b9928be`。上游已经提供 token budget、完整输入准入、水位、动态分块相关配置，以及原生块预留接口。

本项目不从零重写注意力执行器，也不重新拥有物理 KV 内存。小补丁暴露三类接口：逐请求 token 配额、前缀查找后的准入检查、向原生分配器传入其他请求的预留块数。补丁前后源文件散列都写入 manifest，未知源码拒绝应用。

`TraceScheduler` 不实现上述策略接口，因而调用原生调度；它和 `BudgetScheduler` 共用执行时间追踪。类扩展接口比隐式全局 startup patch 更容易审查，但仍绑定具体版本，升级时必须重新审计。

## 逐步执行流程

1. 从真实请求状态构造不可变视图。请求年龄使用 wall-clock arrival；相邻生成进度使用 monotonic clock，两种时间不相减。
2. 为已有 decode 分配一个 token。依据等待时间计算 prefill 的紧迫度；超过等待补偿阈值时，给最老请求一小段推进配额。这是软公平性机制，不是严格无饥饿证明。
3. 在候选分块中，选择预测执行时间满足软预算的较大值。不能满足时仍保留最小推进路径，避免零预算死锁。
4. 原生引擎进行前缀缓存查找后，使用其 coordinator 计算实际新增块需求，包括命中块重新引用的影响。不得只用 `ceil(prompt/block_size)` 代替真实块需求。
5. 将候选请求需求与其他在途请求未来未分配块需求合计。原生分配器继续执行最后的空间检查、引用计数与分配。
6. 每次准入尝试重新核对账本，因为同一步中前面的分配已经改变空闲块和逻辑块表。完成、取消时释放自己的账本项，物理块仍交给原生释放。
7. 执行返回后记录实际配额与耗时，更新有界 EMA 修正。输出采样、停止条件、流式输出由原生处理。

运行列表的顺序还决定原生 FCFS 分支的抢占对象，最终实现保留该顺序。抢占恢复后，即使请求已有输出且已重算完 prompt，也必须继续追上已知输出末尾才能归为普通 decode；不能只看 prompt 边界。

## 耗时模型

特征为：常数项、decode 请求数、decode 上下文长度之和、prefill token 数、prefill 的 token×上下文注意力近似项。使用非负最小二乘拟合执行墙钟时间；非负约束使增加计算量不会在模型中降低预测成本。

这个模型是工程近似，不覆盖所有 attention backend、图捕获档位或大形状非线性。拟合报告必须给出留出误差和矩阵秩；交替步留出只是诊断，不等价于跨负载泛化。执行反馈修正有界，防止单个编译或系统抢占离群值永久放大模型。

## KV 预算

账本只记录未来尚未分配的块。已有逻辑块表中的块不能再计一次；共享前缀的物理引用仍由原生分配器计数。预测 decode 增长使用有限 horizon，并被用户指定的最大输出长度和模型上下文上限截断，不能读取未来实际输出长度。

预留过多会降低并发和吞吐；预留不足仍可能抢占。这是必须通过消融和不同压力等级量化的取舍，不是无条件的“更安全所以更快”。无在途请求时，不用可选的未来增长预测阻塞一个当前输入能够装入的请求。

## 必须验证的不变量

- 每个请求的配额为正且不超过剩余待执行 token；全步总和不超过原生 token budget。
- 自定义调度不修改输出 token 的验证、采样和停止逻辑。
- 新准入不能挪用账本承诺给其他在途请求的空间；最终仍须通过原生分配器。
- 完成、取消和抢占后，没有残留的自定义在途预留。
- 请求全部排空后，原生在用块与空闲块回到合理状态；保留的无引用前缀缓存不等于泄漏。
- 不支持的引擎配置明确拒绝；不能静默宣称多卡或异步兼容。

## 实验顺序

1. 纯策略随机边界测试；真实引擎加载与小请求 smoke。
2. 单请求 greedy 输出 token 对照、块边界长度对照、取消后恢复和请求排空检查。
3. 用校准种子收集原生 trace，拟合耗时并选择上游调优候选；冻结参数。
4. 在不同种子、相同到达轨迹上比较原生、调优基线与完整策略；至少三次独立运行。
5. 去掉耗时预算、去掉 KV 预留，检查收益对应哪个机制。
6. 自然显存、受控 KV 压力、突发负载、低负载和前缀复用分别报告。

不要只展示最好的一组；正确性未通过前不得报告性能胜出。没有收益也要保留原始结果，并明确这是机制实现与问题分析项目，而不是已验证的普适优化。
