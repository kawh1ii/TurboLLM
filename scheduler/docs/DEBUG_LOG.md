# 集成排错记录

## 服务启动健康检查误判

第一次 eager smoke 中，原生服务完成请求后，启动包装进程收到终止信号便退出，但实际 API 子进程尚在关闭；随后新服务的健康检查命中了旧端口。新服务并未真正就绪，客户端因此连接失败。

修复：启动脚本用 `execvpe` 替换自身，使实验管理器直接等待实际 API 进程；同一轮不同策略使用不同端口。失败的启动记录保留为开发排错证据，不纳入成功运行的性能比较。修复后重新执行完整 smoke。

## 分块变化与输出数值稳定性

普通 BF16 eager 模式下，自定义策略与原生策略在 17 个请求中有 1 个逐 token 不一致。该请求的原生 prefill 分配为 255 token，自定义策略分为 128+127 token，首个输出分歧在第 14 个 token。

独立的原生对照只把 token budget 改为 16，也产生 3/17 个差异；其中上述请求的完整输出与自定义策略相同。这说明不能把逐 token 差异简单归因于自定义 KV 管理。此对照同时改变了原生分块与部分批处理形状，尚未定位到某一个具体 kernel 或某次舍入操作。

随后使用上游 `VLLM_BATCH_INVARIANT=1`，原生与自定义策略 17/17 个请求逐 token 一致，包括块边界、长提示词、自然语言和四请求并发；两种策略都通过真实 token 配额与排空后块计数检查。该数值模式有性能代价，严格一致性测试与普通数值模式的性能结果分别列出。

原始证据在 `results/smoke-eager/`、`results/native-numerics/` 和 `results/correctness-invariant/`。不能将 batch-invariant 下的通过，扩大为普通 BF16 模式中任意批处理都会逐 token 一致的保证。参考：[固定版本的官方说明](https://docs.vllm.ai/en/v0.32.0/features/batch_invariance/)。

## 运行队列顺序的隐含语义

开发版为了先处理 decode，重排了原生 RUNNING 列表。但 FCFS 分支在 KV 不足时，会从该列表尾部挑选抢占对象；重排因此同时改变了 victim 选择，部分高压力结果中的重计算增加。

修正后保留原生 RUNNING 顺序。自己的 token 配额总和不超过原生预算，所以早处理的 prefill 即使出现在 decode 前，也不能消费留给后者的配额。开发版源码和已完成测量保存在 `results/development-v1/`，不把这些结果当作最终版本收益。

## 抢占后的输出回放边界

自定义请求分类最初使用 `output > 0 && computed >= prompt` 判断 decode。被抢占的请求已有输出，但重算可能已经越过 prompt、尚未追上历史输出末尾，此时仍应支持多 token 重算。最终版本改为检查 `computed >= max(prompt, total - 1)`，并新增单元回归。第二个开发版本源码和测量保存在 `results/development-v2/`。

最终 0.3.0 版本重新执行了严格测试：17 个边界/自然语言/并发用例全部一致；另外 16 个同时到达的随机 token 请求，在只有 256 个 KV 块的条件下触发真实抢占与重算，完整输出也全部一致。合计 33/33；对应 `results/correctness-final/` 的两个输出对照文件。该回归同时要求所有实际分配不超配额、排空后的空闲块恢复和账本为空。

最终校准/调优/评估使用种子 61 / 62 / 63、64、65。开发版种子与结果不参与最终配置选择，开发中的负面结果和源码快照仍保留供审查。
