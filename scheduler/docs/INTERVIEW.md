# 面试时必须能解释的设计问题

下面是对代码和证据的解释路线，不是应背诵的业绩。性能表述须以最终原始结果为准。

## 到底哪些代码是自己的？

`policy.py` 的耗时特征、候选配额计划、等待补偿和未来块账本；`vllm_scheduler.py` 中的实际请求视图、执行反馈、前缀命中后准入判断和生命周期对接；版本锁定补丁、基线和回归工具。

模型加载、attention backend、Paged KV 块表、引用计数、GPU kernel、原生抢占与采样是上游实现。不能将这些也表述为自己实现。

## 为什么不是换一种方式调 max_num_batched_tokens？

原生全步上限保留不变；自己的计划为不同请求分别给出 quota，并在实际分配处逐一执行。决策会使用上下文长度、decode 紧迫度和预测执行时间。KV 准入是在命中块已知后，根据实际新增需求与其他请求的未来预算决定接纳或跳过。它不是只按 GPU 利用率调整一个全局并发参数。

## 为什么 token 数不能直接等价于执行时间？

decode token 要读取不同长度的历史 KV；prefill 的 attention 工作量随上下文和分块变化。混合批次还有后端、图捕获档位和 kernel 效率等影响。本项目用简化特征拟合墙钟时间，报告误差，并承认它不能精确覆盖全部非线性。

## 耗时从哪里来？

从同步调度完成，到模型结果返回的 `execution_ms`；这是包含执行器及 IPC 的墙钟时间。没有把它称作 CUDA kernel 时间，也没有在缺少 GPU 硬件计数器时声称测到了带宽饱和或 occupancy。

## 已有原生 KV 水位，自己的预留有什么区别？

固定水位预留的是总容量的某个比例。账本核算每个在途请求的未来未分配块，已有块不重复计入；接纳候选时合计其他请求的义务。有限 horizon 是估计，仍可能发生之后的抢占；代价是可能降低并发，需要对照消融。

## 为什么不能自己算 ceil(prompt/block_size) 就准入？

命中前缀的块可能已有引用，也可能目前在可驱逐队列中，重新引用会改变空闲块需求。直接按 token 数算会忽略这些状态。这里调用上游 coordinator 计算实际新增块需求，并让原生分配器做最终检查。

## 谁释放物理 KV？如何避免状态不同步？

只有原生分配器拥有物理块和引用计数。自定义账本只存未来预算。每次准入尝试重新读取当前块表；完成、取消和抢占会清除相应预算。真实 trace 还要验证请求排空、空闲块恢复、账本为空。

## 如何处理长请求饥饿？

按年龄增加紧迫度，超过阈值时给最老 prefill 一个小推进配额。它是软公平性策略，不是数学意义的严格无饥饿保证；KV 空间不足时仍可能需要等待已有请求完成。

## 为什么出现逐 token 不一致？

普通 BF16 模式中，分块和批处理形状可以改变数值路径。项目做了原生对原生的独立控制，并在上游 batch-invariant 模式下做严格输出比较。必须区分“测试观察到一致”“采样逻辑未改”和“任意执行路径必然一致”这三种不同强度的结论。

## 如何证明收益来自自己，而不是一个差基线？

双方固定模型、硬件、编译/图模式、资源、输入和到达轨迹。原生配置与自身 horizon 都只在校准种子上选择，然后冻结，在其他种子上评估；再去掉耗时预算或 KV 预留做消融。即使收益只在高压力场景出现，也要同时报告低负载、吞吐代价和失败请求。

## 为什么没有强行加一个 CUDA 算子？

本项目的核心修改在调度与资源决策路径。只有执行 trace 指向某个实际瓶颈，才值得进一步写 kernel；孤立微基准更快而端到端没有收益，不能代替系统贡献。此项目不宣称具备尚未实现的算子优化成果。
