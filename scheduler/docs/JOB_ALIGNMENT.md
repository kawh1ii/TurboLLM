# 岗位要求与项目证据

以下依据 2026-11-04 查阅的官方公开资料，描述技能匹配，不代表岗位仍在招或个人已满足全部要求。

| 岗位能力 | 本项目的可审查证据 | 不能扩大表述的边界 |
|---|---|---|
| 推理引擎核心模块开发 | 固定版本源码补丁；自定义 Scheduler；真实 token 配额进入原生分配路径 | 没有从零实现整个 vLLM、attention backend 或模型执行器 |
| 批处理与调度 | 根据请求状态和耗时特征生成逐请求配额；等待补偿；上游运行顺序语义审计 | 软目标、单卡原型，未证明最优或硬实时保证 |
| KV 资源管理 | 前缀命中后的实际需求核算；未来块账本；取消、完成、抢占生命周期 | 物理块表、引用计数、GPU 内存分配仍为上游实现 |
| 性能分析 | 请求级 SSE、引擎执行墙钟、调度/规划开销、抢占与重计算计数 | 当前无硬件计数器权限，不能声称实测带宽饱和或 occupancy |
| 工程质量 | 纯策略单元测试、真实 GPU 输出对照、配额与排空不变量、版本和源码散列锁定 | 小样本通过不等于所有模型、后端、批处理形状都已验证 |
| 严谨对照 | 独立校准/调优/评估种子；冻结配置；消融；恢复上游原始源码的无追踪对照 | 有限候选搜索不等于全局最优基线；有限 GPU 结果不等于线上收益 |
| CUDA / Triton 算子开发 | 本项目使用相关执行后端，并理解其数值/图模式约束 | 本次重写没有自行实现新的高性能 GPU 算子，不能写成“精通算子优化” |

## 建议阅读顺序

先读 `DESIGN.md` 和 `policy.py`，手工推演三个请求在一个 token budget 中如何分配；再看 `vllm_scheduler.py` 与小补丁，理解准入前后块表和请求状态的变化；最后用 `DEBUG_LOG.md` 和最终实验报告解释验证过程与代价。面试表述应跟随这些实际证据，而不是把岗位里的所有技术词都加进简历。
